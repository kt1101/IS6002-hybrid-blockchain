Một node Veritas

mọi node chạy cùng mã; chỉ hộp tím (đồng thuận) thay đổi giữa các backend

Thành phần

Thành phầnVai trò
BatcherGom Set thành block (đủ size hoặc hết flush), gắn attestation và bằng chứng đang chờ vào block kế tiếp.
ExecutorÁp dụng block tất định trên mọi node: kiểm version (TSO cho kafka/raft, theo thứ tự block cho tendermint/bft2), ghi Redis, cập nhật SMT; với --verify-sigs=all kiểm chữ ký từng Set.
Sổ cái SMTLeaf = value-version; root digest sau mỗi block; proof Merkle cho một key. Cây được cắt tỉa để bộ nhớ có giới hạn.
consensus.ConsensusBa hàm Submit, Deliver, Close: một dịch vụ total-order broadcast. Mỗi backend nằm trong consensus/<tên>.
Attestor + CertifierKý (h, root_h); gom chữ ký theo height; h được xác nhận khi có Q chữ ký hợp lệ từ Q node khác nhau trên cùng root. Chạy trong apply loop nên tất định.
AccountantTập node bị loại (kèm height và lý do), epoch; kiểm lại bằng chứng đọc trong vòng apply.

Nguyên tắc

  • Chỉ đồng thuận thay đổi. Batcher, Executor, SMT, Certifier, Accountant dùng chung cho kafka, raft, tendermint, bft2; block size như nhau cho mọi backend.
  • Mọi quyết định đều tất định. Attestation và bằng chứng đi trong block, được xử lý theo thứ tự block, nên mọi node trung thực xác nhận cùng root và loại cùng node tại cùng height, không cần giao thức trao đổi thêm.
  • Đồng thuận không phải sửa. Toàn bộ giai đoạn 2–3 nằm trong core, client và harness; adapter đồng thuận không đổi.
  • Đo được. Breakdown thời gian (gom block, chờ đồng thuận, thực thi, ghi sổ cái), byte mạng mỗi block, sidecar .evict, .certs, .ops.csv cho mỗi lượt.

Đường đi của một lần ghi

  1. Client ký key 0x00 value 0x00 version bằng khóa Ed25519 rồi gửi Set tới node chính của nó.
  2. Node kiểm chữ ký (ingress), đưa Set vào batcher.
  3. Batcher gửi block vào đồng thuận (Submit); block có thể kèm attestation và bằng chứng của node.
  4. Đồng thuận trả block cho mọi node theo cùng thứ tự (Deliver).
  5. Apply loop của mỗi node gọi Executor: kiểm version (và chữ ký nếu all), ghi Redis, cập nhật SMT, tính root mới.
  6. Certifier xử lý các attestation trong block; ở height được attest, node ký (h, root_h) để gửi trong block kế tiếp.
  7. Ở chế độ sync, node đề xuất trả lời client khi block của nó đã được áp dụng.

Đường đi của một lần đọc certified

  1. Client gọi GetVerified (tùy chọn signed).
  2. Node lấy value, version, proof và root tại một height đã ký, trong cùng một lần giữ khóa của executor, nên proof luôn khớp root.
  3. Node chờ tới khi height đó được xác nhận (tổng tối đa 5 s), rồi trả về kèm Q attestation; nếu signed thì ký cả phản hồi.
  4. Client kiểm proof theo root, kiểm ≥ Q chữ ký hợp lệ từ các node khác nhau trên đúng (h, root).
  5. Không đạt: từ chối giá trị, chuyển node (failover); nếu phản hồi có chữ ký thì gửi ReportEvidence tới một node khác.

Giá phải trả: đọc phải chờ height kế tiếp được attest (E9: read p50 ~92–102 ms ở attest 1, so với 1,1 ms đọc thường; E10: 93–112 ms ở workload a).
